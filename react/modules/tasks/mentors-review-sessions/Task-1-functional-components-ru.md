# План проведения сессии Code Review с ментором: Task 1 Functional components - Weather Dashboard

Проведение онлайн-сессии Code Review требует четкого регламента. Предложенный алгоритм взаимодействия позволит объективно оценить качество кода, инженерную самостоятельность и осознанное использование AI-инструментов, подтверждая, что студент остается владельцем своей кодовой базы.

### Шаг 1. Оценка теоретических знаний (Theoretical Knowledge Evaluation)

Глубокое понимание теоретических основ React является главным условием создания масштабируемой архитектуры и эффективной профилактики технического долга. Умение студента давать краткие, технически точные ответы с опорой на официальную документацию и первоисточники демонстрирует зрелость его инженерного мышления и способность к профессиональной коммуникации в команде.

### 1.1. История React

1. В чем заключается фундаментальная философия React «UI как функция состояния» и кто стоял у истоков библиотеки?

### 1.2. React Hooks

1. В чем преимущества React Hooks перед классовыми компонентами?

4. Как хук `useContext` позволяет избегать проп-дриллинга (prop drilling)?
5. Для чего используется `useRef` и чем он отличается от обычного состояния?

### 1.4. Тестирование React-приложений

1. Какие инструменты используются для настройки тестирования в связке с Vite?

3. В чем различие между Unit и Integration тестированием в React?

### Шаг 2. Предварительный анализ деплоя, структуры PR и штрафных критериев ментором (можно провести до встречи или параллельно с шагами 3-5, пока студент демонстрирует приложение, отвечает на вопросы и выполняет live-coding)

### Шаг 4. Инспекция исходного кода в IDE, глубокий разбор проекта "Weather Dashboard" (10 Deep-Dive Project Questions)

Оценка понимания студентом архитектурных решений, принятых в проекте "Weather Dashboard", и умения аргументировать их выбор.

- **Совместный разбор:** Анализ декомпозиции UI, архитектуры кастомных хуков, чистоты функций/редусеров, строгости TypeScript, настроек линтеров и тестового окружения.

Ниже — 10 вопросов deep-dive, которые входят в оценку Шага 4.

1. **Управление состоянием коллекции локаций:**

Оцените ваш выбор между `useState` и `useReducer` для управления коллекцией сохраненных локаций и жизненным циклом запросов (`Status: idle | loading | success | error`). Как этот выбор зафиксирован в проектной документации (например, в `CHANGELOG.md`)?

2. **Кастомный хук useLocalStorage и краевые случаи:**

Проанализируйте реализацию хука `useLocalStorage`. Каким образом в нем обработаны краевые случаи работы с `localStorage` (ошибки парсинга невалидного JSON, отсутствие доступа в инкогнито, синхронизация при изменении первоначального ключа)?

3. **Сайд-эффекты, сетевые запросы и защита от гонки состояний:**

Обоснуйте структуру `useEffect`, используемого для выполнения запросов к API Open-Meteo. Реализована ли в нем защита от «гонки состояний» (stale responses / race conditions) и дублирующих запросов при размонтировании компонента или быстрой смене параметров?

4. **Архитектура Error Boundary и механизм тестирования:**

Проанализируйте реализацию классового компонента `ErrorBoundary`. Каким образом устроена кнопка-триггер для проверки его работы и как обеспечивается логирование перехваченной ошибки?

5. **Строгость типизации и контракты данных:**

Сравните предложенные интерфейсы `SavedLocation` и `Units` с вашей реализацией. Используются ли конструкции `any` или `@ts-ignore`? Каким образом обеспечена типизация кэшированных данных (`fetchedAt`) и статуса выполнения запроса?

6. **Стратегия тестирования и мокирование внешних сервисов:**

Оцените полноту модульного тестирования. Каким образом с помощью Vitest mocks или MSW были замокированы асинхронные вызовы к API Open-Meteo при проверке поведения UI в состояниях `loading` и `error`?

7. **Проверка покрытия тестами (Coverage Thresholds):**

Проанализируйте итоговые метрики покрытия тестами. Был ли достигнут обязательный порог в ≥80% по операторам (statements) и каковы значения по ветвлениям и функциям?

8. **Автоматизация качества кода (Oxlint, Oxfmt, Husky):**

Обоснуйте настройку цепочки Oxlint, Oxfmt и Husky. Каким образом пре-коммит хук защищает репозиторий от попадания неотформатированного кода или ошибок линтера?

9. **Инженерная самостоятельность и AI-коучинг:**

Сравните первоначальные рекомендации AI-ассистента с финальным кодом проекта. Какие архитектурные решения вы приняли полностью самостоятельно, отклонив сгенерированные AI варианты?

10. **Декомпозиция UI и отсутствие сторонних библиотек:**

По какому принципу UI был декомпозирован на компоненты (`SearchBar`, `WeatherCard`, `SavedLocations`)?

### Шаг 5. Live-coding (Practical Code Modification)

Проверка понимания студентом собственной кодовой базы, скорости поиска файлов, навыков отладки.

### Практические задания для Live-coding (выполняется 1 задание: либо 1 из списка ниже, либо эквивалентное по сложности задание ментора)

1. **Добавление кнопки «Очистить все» (State & Storage):**

Добавить в компонент списка сохраненных локаций кнопку «Очистить список», которая при клике полностью сбрасывает состояние сохраненных локаций и очищает соответствующую запись в `localStorage`.

2. **Локальная валидация ввода в SearchBar (UI Validation):**

Реализовать локальную валидацию в контролируемом поле ввода `SearchBar`. Если пользователь пытается отправить пустую строку или строку из одних пробелов, отобразить под полем локальное текстовое сообщение об ошибке («Введите название города») без отправки сетевого запроса.

3. **Логирование сериализации в useLocalStorage (Custom Hook Modification):**

Модифицировать кастомный хук `useLocalStorage`, добавив в блок catch функции сохранения данных вывод предупреждения в консоль (`console.warn`), если переданное значение не удается успешно сериализовать через `JSON.stringify`.

4. **Добавление кнопки тестового сбоя для Error Boundary (Error Handling):**

Добавить внутри компонента карточки погоды (`WeatherCard`) кнопку «Спровоцировать ошибку», клик по которой инициирует генерацию исключения `throw new Error("Live Coding Test Error")`.

5. **Написание юнит-теста переключения единиц измерения (Testing):**

Написать один новый модульный тест с использованием Vitest и React Testing Library, проверяющий, что единицы измерения (`metric / imperial`) корректно меняют свое значение при клике на соответствующий переключатель.
