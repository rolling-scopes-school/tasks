# Clean Code

## Навыки

`clean code` `рефакторинг` `ESLint` `Prettier` `Husky` `JavaScript` `Git` `GitHub`

## Что делать

Перед вами небольшое работающее TODO-приложение: задачи можно добавлять, редактировать, удалять и переносить между списками «Todo» и «Completed». Всё это работает и должно продолжить работать после ваших правок. Ломать и чинить здесь нечего.

Проблема в другом: этот код тяжело читать и страшно менять. В нём есть типичные признаки проблемного кода из модуля Clean Code. Какие именно и где, вам предстоит найти самим.

Задание построено так, как работают с унаследованным проектом: **сначала машина, потом человек**.

**Часть 1 — инструменты.** Вы настраиваете ESLint, Prettier и Husky и отдаёте им всё механическое. Когда линтер замолчит, код всё ещё будет плохим. Это главный результат части: вы увидите, что остаётся человеку.

**Часть 2 — смысл.** Вы наводите порядок в том, чего ни один инструмент не найдёт. Каждое изменение отдельным коммитом, чтобы его можно было прочитать.

**Часть 3 — необязательная.** Вы пишете инструкцию для AI-помощника по правилам этого задания и проводите ревью собственного решения. Баллов не даёт.

В конце вы проверяете приложение по чек-листу поведения и объясняете в описании Pull Request три своих решения.

## Требования

- Работайте в **личном публичном форке** репозитория [clean-code-todo](https://github.com/HelgaZhizhka/clean-code-todo).
- Создайте ветку от `main` и ведите всю работу в ней. `main` не изменяйте.
- **Функциональность приложения должна остаться прежней.** Проверяется по чек-листу поведения ниже.
- Каждое изменение — отдельный коммит по [конвенции коммитов](https://rs.school/docs/git-convention). Сообщение отражает суть изменения, а не «fix» и «update».
- Описание Pull Request оформляется по [схеме RS School](https://rs.school/docs/mentoring/pull-request-review-process#pull-request-requirements-pr) и дополняется пунктами из раздела «Что писать в описании Pull Request».
- **Механические правки не смешиваются со смысловыми.** Форматирование, автофиксы линтера и смысловые изменения идут отдельными коммитами.
- Prettier обязан принимать `index.html` и `style.css`. Сейчас он их не принимает: Prettier сам скажет, где и что не так. Исключать файлы через `.prettierignore` нельзя.
- В стартовом репозитории есть файл `.github/workflows/check.yml`. Он запускается на каждый Pull Request, проверяет настройку инструментов и прогоняет линтер и форматтер. **Изменять или удалять его нельзя.**

### Часть 1. Инструменты

К концу части в репозитории должно быть:

- `.gitignore`, в котором есть `node_modules`;
- `package.json` со скриптами `lint` и `format`: их имена сверяет CI;
- `eslint.config.js`: рекомендованный набор правил, глобальные переменные браузера, правила `no-var`, `prefer-const`, `no-console`;
- `.prettierrc`;
- `.prettierignore`, в котором есть лок-файл пакетного менеджера и папка `.github`: первый генерируется, второй менять нельзя;
- `.husky/pre-commit`, который через lint-staged проверяет файлы из коммита.

Как этого добиться, разберитесь по модулю и документации. Готовые наборы правил вроде Airbnb или Standard не используйте: конфиг собирается из рекомендованного набора и правил, которые вы добавили сами и понимаете.

**Порядок коммитов** — требование, по нему ревьюер читает вашу работу:

1. Настройка инструментов. Кода приложения не касается.
2. Исправление синтаксиса в HTML и CSS.
3. Форматирование.
4. Автофиксы линтера.
5. Остальные замечания линтера, исправленные руками.
6. Husky и lint-staged.

Перед первым коммитом запустите линтер и запишите результат: сколько проблем он нашёл и сколько из них помечены как исправимые автоматически. Эти цифры понадобятся в описании PR.

После шестого коммита каждый ваш коммит проходит через линтер и форматтер. Если что-то не проходит, чините код, а не хук.

### Часть 2. Смысл

Линтер молчит, код плохой. Найдите и исправьте, каждое отдельным коммитом:

- мёртвый код;
- дублирование: обработчиков и логики. Не всё похожее нужно объединять, но каждое решение нужно обосновать;
- имена, которые не читаются без комментариев;
- комментарии, которые пересказывают код;
- функции, которые не читаются целиком.

Что считать проблемой и как её называть, смотрите в модуле Clean Code и в материалах, на которые он ссылается.

### Часть 3. Необязательная: свой AI-ревьюер

Баллов не даёт и на оценку не влияет.

Напишите инструкцию для AI-помощника в файле `review-instructions.md` в корне проекта. Стройте её как постановку задачи: **цель** — что помощник должен сделать; **границы** — что проверять, чего не трогать; **критерий готовности** — как понять, что ревью закончено; **формат вывода** — куда и в каком виде помощник отдаёт результат: например, отчёт в файле `review-report.md` на русском, замечания сгруппированы по категориям из задания, каждое из четырёх частей, как в модуле Clean Code: место в коде, проблема, условие, при котором она проявляется, способ проверить исправление.

Подойдёт любой AI-помощник, которым вы уже пользуетесь: чат вроде ChatGPT, Claude или Gemini, агент в терминале или редакторе вроде Claude Code, Codex, Pi или Cursor, расширение для VS Code. Способ один: дайте помощнику инструкцию и доступ к коду, как именно — зависит от инструмента. Платная подписка не нужна: у чатов есть бесплатный тариф, а Pi работает с бесплатными моделями через OpenRouter.

Помощник **не редактирует файлы**, он только анализирует и объясняет. Из его замечаний выберите три и разберите в PR: какие принимаете, какие отклоняете и почему. Решения принимаете вы.

## Чек-лист поведения

Пройдите руками на своём деплое и отметьте в описании PR. Ревьюер пройдёт его же.

- [ ] Новая задача добавляется в список «Todo»
- [ ] Задача в списке «Todo» редактируется
- [ ] Задача удаляется из списка «Todo»
- [ ] Чекбокс переносит задачу в «Completed»
- [ ] Задача в списке «Completed» редактируется
- [ ] Задача удаляется из списка «Completed»
- [ ] Снятие чекбокса возвращает задачу в «Todo»
- [ ] Пустая задача не добавляется
- [ ] Внешний вид приложения не изменился
- [ ] Анимация кнопки удаления работает

## Что писать в описании Pull Request

Кроме [стандартных пунктов](https://rs.school/docs/mentoring/pull-request-review-process#pull-request-requirements-pr):

1. **Ссылка на деплой.**
2. **Результат первого запуска линтера:** сколько проблем нашёл, сколько из них исправил `--fix`, что пришлось делать руками и почему.
3. **Отмеченный чек-лист поведения.**
4. **Объяснение трёх изменений из части 2:** какая была проблема → что сделали → как убедились, что поведение не изменилось.
5. **Если делали часть 3:** три замечания помощника, какие приняли, какие отклонили и почему.

Пункт 4 — самое важное в задании. Умение назвать проблему и обосновать решение отличает рефакторинг от перестановки строк местами.

## Чего делать не нужно

- Переписывать приложение на фреймворк, добавлять сборщик.
- Применять DRY, KISS и YAGNI «по одному разу», чтобы показать знание терминов. Изменение должно решать конкретную проблему.
- Дробить функции только потому, что они длинные, и объединять код только потому, что он похож.
- Менять или удалять файл workflow в `.github/workflows`.

## Как сдавать

1. Сделайте **Fork** репозитория [clean-code-todo](https://github.com/HelgaZhizhka/clean-code-todo).
2. Откройте вкладку **Actions** в своём форке и включите workflows кнопкой «I understand my workflows, go ahead and enable them». В форках GitHub выключает их по умолчанию.
3. Создайте ветку от `main` и работайте в ней.
4. Задеплойте результат. Подойдёт GitHub Pages или любой хостинг статики. В настройках GitHub Pages выберите вашу рабочую ветку, а не `main`.
5. Откройте **Pull Request** из своей ветки в `main` **своего** форка. Не мержите его.
6. Дождитесь, пока проверка «ESLint, Prettier, Husky» на странице PR станет зелёной. Если она красная, откройте её: причина написана на русском.
7. Оформите описание PR по пунктам выше.
8. Отправьте ссылку на Pull Request через [rs app](https://app.rs.school/) → **Cross-Check: Submit**.

## Cross-check

Задание проверяется через [cross-check](https://rs.school/docs/cross-check-flow).

### Как проверять

Ревьюер смотрит пять мест, каждое отвечает за свой блок критериев:

| Блок             | Где смотреть                                                                                                                                                                                                            |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Настройка        | Файлы в репозитории: `.gitignore`, `package.json`, конфиги ESLint и Prettier, `.husky/pre-commit`. Статус проверки «ESLint, Prettier, Husky»: внизу вкладки Conversation в PR над кнопкой слияния или на вкладке Checks |
| История коммитов | Вкладка Commits в PR: порядок и содержимое коммитов, diff каждого                                                                                                                                                       |
| Рефакторинг      | Итоговый `app.js`                                                                                                                                                                                                       |
| Поведение        | Деплой: пройти чек-лист руками                                                                                                                                                                                          |
| Объяснения       | Описание PR                                                                                                                                                                                                             |

Клонировать репозиторий не нужно: всё, что требует запуска, уже проверила CI. Если проверка красная, а автор утверждает, что всё работает, верьте проверке.

## Критерии оценки

**Максимальный балл: 150.** Сумма по всем пунктам — 170; запас сглаживает неточности проверки.

### Настройка (30)

- `.gitignore` есть, `node_modules` не закоммичен — **+5**
- ESLint: `eslint.config.js` с рекомендованным набором, `no-var`, `prefer-const`, `no-console`; скрипт `lint` — **+10**
- Prettier: конфиг есть, `index.html` и `style.css` не исключены из проверки — **+5**
- Husky и lint-staged: `.husky/pre-commit` проверяет, а не правит — **+5**
- Проверка CI зелёная, файл workflow не изменён — **+5**

### История коммитов (30)

- Отдельный коммит настройки, без изменений в коде приложения — **+5**
- Отдельный коммит только с форматированием — **+10**
- Отдельный коммит с автофиксами линтера — **+5**
- Смысловые изменения отдельными коммитами, сообщения отражают суть — **+10**

### Рефакторинг (60)

Засчитывается любое решение, дающее нужный результат.

- Мёртвый код удалён — **+10**
- Дублирование обработчиков устранено — **+10**
- Дублирование логики устранено или решение оставить его обосновано — **+10**
- Имена переменных и функций понятны без комментариев — **+10**
- Комментарии, пересказывающие код, удалены; оставшиеся объясняют причину — **+10**
- Длинные функции разделены, упрощены или обоснованно оставлены как есть — **+10**

### Поведение (20)

Ревьюер проходит чек-лист на деплое сам.

- Пункты 1–8: задачи добавляются, редактируются, удаляются и переносятся между списками — **+10**
- Пункты 9–10: внешний вид не изменился, анимация удаления работает — **+10**

### Объяснения (30)

- Три объяснения, по **+10** за каждое: названа конкретная проблема, объяснено решение, указан способ проверки.

### Штрафы

- Pull Request оформлен не по схеме или нет ссылки на рабочий деплой — **−50**
- Коммиты не соответствуют конвенции — **−50**
- Приложение не работает после изменений — **−50**
