# Пошаговый гайд: командный онлайн-магазин

Этот гайд поможет паре, которая впервые вместе создаёт проект. Он показывает один из возможных путей: GitHub Projects, общий репозиторий, TypeScript, Vite и Vitest. Используйте знакомые инструменты, если вам так удобнее. Условия сдачи и критерии оценки находятся в [основном задании](README.md).

## 1. Договоритесь о проекте

Начните с короткой встречи. Выберите название магазина и товары — например, книги, растения или настольные игры. Договоритесь о времени работы, связи и ближайшей встрече. Определите небольшой результат, который сможете завершить вместе.

Ниже — **пример функциональности**, а не дополнительный список обязательных требований или балльных критериев. Можно изменить набор товаров, фильтров и возможностей под идею команды. Обязательный минимум для магазина и любого другого проекта указан в [техническом минимуме основного задания](README.md#технический-минимум--обязателен-для-любого-проекта).

### Страницы и переходы

- Приложение — одностраничное (SPA). При открытии приложения пользователь видит страницу «О нас»: описание магазина, участников команды и краткий вклад каждого. На ней разместите кнопку или ссылку перехода в каталог.
- Все экраны — самостоятельные состояния приложения со своим адресом. Используйте hash-адреса: `#/about`, `#/catalog`, `#/cart` — они работают на GitHub Pages без дополнительных настроек; адреса без `#` (history API) требуют файлов-заглушек и в этом проекте не используются. Попапы (подтверждение действия, сообщение об ошибке) экранами не считаются: у экрана есть адрес.
- Меню доступно на всех экранах; кнопка «назад» в браузере возвращает к предыдущему экрану; при открытии адреса напрямую или перезагрузке страницы нужный экран восстанавливается.
- Интерфейс создаётся кодом на TypeScript через DOM API — шаблон `vanilla-ts` для этого и взят; UI-фреймворки (React, Vue, Angular) в этом проекте не используются. В `index.html` внутри `<body>` остаются только строка подключения скрипта и пустой корневой контейнер.

### Каталог и карточки товаров

Подготовьте, например, 8–12 товаров не менее чем в двух категориях и храните их в файле проекта. Для каждого товара задайте уникальный идентификатор, название, категорию и цену. При желании добавьте изображение и краткое описание.

На карточке покажите название, категорию, цену, изображение при его наличии и кнопку «В корзину». После нажатия товар появляется в корзине; если он уже добавлен, его количество увеличивается, а новая строка не создаётся.

### Поиск, фильтры и сортировка

- **Поиск:** поле находит товары по части названия, без учёта регистра. Пустая строка показывает все товары, подходящие под остальные фильтры.
- **Категория:** можно выбрать одну категорию или «Все категории».
- **Цена:** поля «От» и «До» ограничивают диапазон включительно; пустая граница не применяется.
- **Сортировка:** исходный порядок, цена по возрастанию и по убыванию.
- Поиск, категория и диапазон цены действуют одновременно, сортировка применяется к результату. Если ничего не найдено, покажите сообщение. Кнопка сброса возвращает исходные значения фильтров и сортировки.

### Корзина (промокод — по желанию)

- Для каждого товара покажите название, цену за единицу, количество и стоимость строки.
- Кнопки «+» и «−» изменяют количество; уменьшать его ниже 1 нельзя. Удаление отдельной кнопкой убирает товар из корзины.
- Покажите общую стоимость как сумму стоимости всех строк. Для пустой корзины покажите сообщение и сумму 0.
- Сохраняйте корзину в `localStorage`, чтобы всё добавленное было видно после перезагрузки страницы. Это обязательное требование технического минимума основного задания.
- По желанию добавьте третье действие — промокод: например, `SALE10` даёт скидку 10% на общую стоимость; неизвестный код скидку не применяет и сопровождается сообщением. Повторный ввод не накапливает скидку. Правила и отображение скидки команда может определить иначе.

Оплата, регистрация, настоящий сервер и база данных для этого примера не нужны.

Сначала добейтесь работающего минимума, затем улучшайте внешний вид и добавляйте функции. Каждый участник должен понимать весь проект и иметь собственные задачи, о которых сможет рассказать на интервью.

## 2. Создайте репозиторий и пригласите напарника

1. Один участник создаёт на GitHub публичный репозиторий, например `team-store`, с файлом `README.md`. Создатель — владелец репозитория.
2. Владелец открывает **Settings → Collaborators → Add people** и приглашает напарника по GitHub-логину. Напарник принимает приглашение. [Инструкция GitHub](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/repository-access-and-collaboration/inviting-collaborators-to-a-personal-repository).
3. Оба участника клонируют один и тот же репозиторий на свои компьютеры. Подставьте адрес вашего репозитория:

   ```bash
   git clone https://github.com/OWNER/team-store.git
   cd team-store
   ```

4. Убедитесь, что оба видят репозиторий и могут создавать в нём ветки. Не публикуйте токены, пароли и другие секреты в коде или файлах проекта.

## 3. Создайте доску задач

Можно использовать Jira, GitHub Projects или аналог. Для примера ниже выбраны GitHub Issues и Projects:

1. В репозитории откройте **Issues → New issue** и создайте несколько задач. Например: «Настроить проект», «Страница о команде», «Переходы между экранами и восстановление адреса», «Каталог товаров», «Поиск и фильтры», «Добавление в корзину», «Подсчёт суммы», «Сохранение корзины в localStorage», «Деплой».
2. В профиле GitHub откройте **Projects → New project**, создайте проект и выберите представление **Board**. Добавьте созданные issues на доску.
3. Договоритесь о статусах, например **Todo**, **In Progress**, **In Review** и **Done**. Назначьте ответственного за каждую задачу и укажите её объём в описании.
4. Пригласите напарника в настройки проекта с правом редактирования: доступ к репозиторию и доступ к доске настраиваются отдельно. [Настройка доступа к проекту](https://docs.github.com/en/issues/planning-and-tracking-with-projects/managing-your-project/managing-access-to-your-projects).
5. Перед началом работы перенесите задачу в **In Progress**, после создания PR — в **In Review**, после принятия изменений — в **Done**. При необходимости меняйте план и обсуждайте это с напарником.

Доска может быть закрытой, но оба участника должны иметь к ней доступ. Для интервью покажите её на экране; ссылку на доску приложите к сдаче.

## 4. Подготовьте приложение

Один участник создаёт основу проекта и отправляет её в репозиторий через PR. Второй проверяет изменения, после чего оба работают с общей основой. У обоих должны быть установлены Git и подходящая версия Node.js с npm: требования к версии Node.js смотрите в [руководстве Vite](https://vite.dev/guide/).

В отдельной пустой папке создайте проект:

```bash
npm create vite@latest team-store-app -- --template vanilla-ts
cd team-store-app
npm install
npm install -D vitest
npm pkg set "scripts.test=vitest run --passWithNoTests"
npm run dev
```

Откройте адрес, который напечатает Vite, и убедитесь, что стартовая страница работает. Остановите сервер сочетанием `Ctrl+C`. Команда `npm test` запустит тесты; `--passWithNoTests` позволит настройке пройти до появления первого теста. Когда тесты появятся, уберите флаг из `package.json`: с ним проверки CI останутся зелёными, даже если тестов в проекте нет. Ошибки в тестах приводят к ошибке команды.

Перенесите созданные файлы в клонированный `team-store`: например, скопируйте содержимое `team-store-app`, сохранив Git-репозиторий и существующий `README.md`, а не вложенную папку с проектом. Папку `node_modules` копировать и коммитить не нужно. Проверьте, что `.gitignore` исключает `node_modules` и `dist`, а `package-lock.json` присутствует: он нужен для одинаковой установки зависимостей.

Из корня клонированного репозитория проверьте:

```bash
npm ci
npm run build
npm test
```

Создайте ветку настройки, закоммитьте файлы проекта, отправьте её на GitHub и откройте PR. После ревью и слияния второй участник обновляет локальный `main` и выполняет `npm ci`. Если оба начали настройку одновременно, сначала договоритесь, какую общую основу оставляете.

## 5. Работайте над задачами через ветки и PR

Для каждой задачи начинайте с актуального `main`:

```bash
git switch main
git pull origin main
git switch -c feature/catalog
```

Замените `feature/catalog` на имя своей задачи. После изменений запустите проект и подходящие проверки, затем создайте коммит и отправьте ветку:

```bash
git add .
git commit -m "feat: add product catalog"
git push -u origin feature/catalog
```

На GitHub откройте PR из своей ветки в `main` общего репозитория. В описании укажите, что сделано, как проверить результат и какая задача на доске закрывается. Попросите напарника посмотреть код и оставить комментарии. Обсудите замечания, внесите необходимые изменения и объедините PR. Затем второй участник обновляет свой `main` перед началом следующей задачи.

Если Git сообщает о конфликте, не удаляйте чужие изменения: вместе посмотрите, какие строки изменились, договоритесь об итоговом варианте, разрешите конфликт и снова запустите проверки.

## 6. Настройте автоматические проверки

CI — это автоматический запуск команд проекта на GitHub. Он помогает паре заметить ошибку до слияния PR. Сначала убедитесь, что `npm ci`, `npm run build` и `npm test` работают локально и файлы `package.json` и `package-lock.json` закоммичены.

Создайте в репозитории файл `.github/workflows/ci.yml`:

```yaml
name: Проверки проекта

on:
  push:
    branches: [main]
  pull_request:

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm
      - run: npm ci
      - run: npm run build
      - run: npm test
```

Если выбранная версия Vite требует более новую версию Node.js, укажите подходящую версию в `node-version`. Откройте PR с файлом workflow и посмотрите результат во вкладке **Actions** или **Checks** PR. Если проверка упала, откройте её журнал, найдите команду с ошибкой и исправьте причину. После появления тестов проверьте, что они действительно запускаются: пустой набор намеренно не считается ошибкой.

ESLint и Prettier можно настроить по материалам недели 7 и добавить в CI их команды, когда они заработают локально. CI и конкретный набор инструментов в этом гайде — рекомендуемый способ организации работы, а не отдельные балльные критерии.

## 7. Опубликуйте проект

Один из вариантов — GitHub Pages:

1. В настройках репозитория откройте **Settings → Pages** и в разделе **Build and deployment** выберите источник **GitHub Actions**.
2. Настройте `base` в Vite для адреса вашего сайта. Если сайт расположен по адресу `https://OWNER.github.io/team-store/`, значение будет `/team-store/`; имя должно совпадать с именем репозитория. Для сайта в корне домена настройка другая.
3. Добавьте workflow сборки и публикации по [руководству Vite по GitHub Pages](https://vite.dev/guide/static-deploy.html#github-pages). Это отдельный workflow от проверок CI выше.
4. После слияния workflow в `main` дождитесь завершения публикации во вкладке **Actions**, откройте выданный адрес и проверьте приложение, в том числе в режиме инкогнито.

Hash-адреса (`#/about`, `#/catalog`, `#/cart`) работают на GitHub Pages без дополнительных настроек: адрес после `#` сервер не запрашивает, экран восстанавливается из хеша самим приложением.

### Альтернатива: Netlify и предварительный просмотр PR

[Netlify](https://www.netlify.com/) удобно использовать для командной работы: после подключения GitHub-репозитория сервис собирает основную версию приложения и создаёт отдельный **Deploy Preview** для Pull Request. Напарник может открыть ссылку и посмотреть изменения до слияния.

1. Войдите в Netlify, создайте проект, выберите импорт существующего проекта из GitHub и подключите общий репозиторий. Выберите `main` как production-ветку.
2. Для проекта из этого гайда укажите команду сборки `npm run build` и папку публикации `dist`. Запустите первый деплой.
3. Откройте Pull Request в `main` и дождитесь сборки. Статус Netlify и ссылка на предварительную версию появятся в PR; при включённых уведомлениях Netlify также добавит комментарий со ссылкой. Новые коммиты в PR обновляют предварительную версию.
4. После слияния изменений в `main` дождитесь обновления основной версии сайта. Добавьте её адрес в описание PR для сдачи и проверьте, что он открывается в режиме инкогнито.

Если ссылка или комментарий не появились, проверьте настройки Deploy Previews и уведомлений проекта в Netlify. Подробнее — в [документации Netlify](https://docs.netlify.com/deploy/deploy-types/deploy-previews/).

Можно использовать и другой хостинг статики. Важно, чтобы проверяющие могли открыть опубликованное приложение по ссылке.

## 8. Подготовьтесь к интервью и сдаче

Выберите функцию проекта с несколькими сценариями и заранее напишите для неё подготовленные unit-тесты: по техническому минимуму модуль логики должен иметь тесты, запускаемые одной командой (`npm test`). На live coding отведите ориентировочно **7–10 минут**: на записи сначала покажите запуск подготовленных тестов, объясните функцию и варианты входных данных, затем напишите во время записи несколько содержательных новых тестов, запустите их и разберите результат; удалять существующие тесты не нужно.

Например, можно тестировать функцию расчёта корзины, которая получает товары с ценой и количеством и промокод, а возвращает сумму до скидки, размер скидки и итог. Для правил примера выше полезно проверить:

- несколько разных товаров и количество больше одного;
- пустую корзину;
- действующий `SALE10` и неизвестный промокод;
- корректность итоговой суммы и то, что скидка не применяется повторно.

Другой вариант — функция фильтрации товаров: проверить поиск без учёта регистра, категорию, границы цены, сочетание фильтров и отсутствие совпадений. Не обязательно охватить все варианты: выберите достаточно разные сценарии, объясните их и напишите тесты для тех, которые успеете содержательно разобрать. Промокод используйте в примерах только если он действительно реализован, иначе берите расчёт суммы корзины или фильтрацию товаров. Используйте функцию своего проекта и запускайте тесты командой, настроенной вашей командой, например `npm test`.

Перед записью отдельно прогоните сценарий демонстрации — [пункт 8 технического минимума основного задания](README.md#8-как-подтвердить-на-записи-сценарий-демонстрации): по нему проверяющий подтверждает, что приложение выполнило обязательные требования. На демонстрацию в интервью отведите ориентировочно 3–5 минут.

Каждый участник готовит отдельную запись, где он — кандидат, и собственный PR для сдачи. PR содержит описание проекта и вклада участника, ссылки на приложение, репозиторий, доску и интервью. Подробный порядок, вопросы и критерии — в [основном задании](README.md#как-сдавать).
