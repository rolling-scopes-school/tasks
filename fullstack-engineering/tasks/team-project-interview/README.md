# Командный проект и интервью

## Что предстоит сделать

Объединитесь в пару, вместе придумайте и разработайте небольшое приложение, организуйте работу с помощью доски задач и GitHub, а затем проведите друг с другом тренировочные интервью.

У задания две главные цели: попробовать командную разработку и научиться рассказывать о своей работе на собеседовании. Проект должен быть достаточно небольшим, чтобы у вас осталось время на общение, взаимное ревью и интервью.

На cross-check каждый участник отправляет **свой Pull Request** с описанием проекта и личного вклада, ссылками на приложение, репозиторий, доску задач и запись интервью, в котором он выступает кандидатом. Критерии оцениваются по тому, что проверяющий увидит и услышит в видео; остальные сведения и ссылки дают контекст о проекте и командной работе.

## Поиск напарника

Зарегистрируйтесь на [сайте для поиска напарника](https://144.31.16.205/) — он поможет найти товарища для выполнения задания и сформировать команду из двух человек. Обсудить совместную работу также можно в чате курса в Discord.

## Часть 1. Проект

Выберите один из вариантов:

1. **Простой онлайн-магазин:** покажите список товаров, добавление и удаление товара из корзины и общую стоимость выбранных товаров. Данные можно хранить непосредственно в проекте.
2. **Свой проект:** придумайте небольшое приложение на любую тему. Например, список задач, каталог фильмов, планировщик или игру. Определите несколько связанных действий пользователя, которые команда сможет реализовать за отведённое время.

Если вы выбрали магазин и не знаете, с чего начать, воспользуйтесь [пошаговым гайдом по магазину и командной работе](store-guide.md).

Для любого варианта:

- Согласуйте небольшой объём работы, распределите задачи и создайте работающее приложение.
- Сделайте стартовую страницу «О нас», которая открывается при загрузке приложения. На ней расскажите, что делает приложение, представьте участников команды — имена или GitHub-логины и краткое описание вклада каждого — и разместите кнопку или ссылку, с которой пользователь переходит к основной работе с приложением.
- Выполните [технический минимум](#технический-минимум--обязателен-для-любого-проекта) — требования к приложению, одинаковые для магазина и для проекта собственной идеи.
- Используйте общий репозиторий и опубликуйте приложение, чтобы его можно было открыть по ссылке.
- Предусмотрите хотя бы одну функцию с понятным результатом, которую можно покрыть unit-тестами на интервью.
- Приложение должно быть написано на TypeScript. В качестве тест-раннера используйте Jest или Vitest. Остальные инструменты выбирайте те, которые знакомы обоим участникам, — с учётом ограничений технического минимума (пункт 1: SPA без UI-фреймворков).

Внешний API, собственный сервер, сложный дизайн и дополнительные функции можно добавить по желанию — сервер разрешён, но не обязателен. Функциональность проекта нужна как основа для командной работы и интервью; отдельного списка баллов за кнопки, дизайн или количество возможностей нет.

### Технический минимум — обязателен для любого проекта

Эти требования обязательны для **любой** темы проекта: и для интернет-магазина из условия, и для приложения собственной идеи. Оценивается только то, что видно на записи интервью — по ней же cross-check проверяет и само приложение. В конце есть готовый сценарий демонстрации. Нарушение любого пункта, видимого на записи, — штраф −150 (подраздел «Штрафы» в критериях оценки).

#### 1. SPA без UI-фреймворков

- Приложение — одностраничное (SPA): экраны переключаются **без полной перезагрузки страницы**. Используйте hash-адреса: `#/about`, `#/catalog`, `#/cart` — такой адрес работает на GitHub Pages без дополнительных настроек. Адреса без `#` (history API) на GitHub Pages требуют файлов-заглушек вроде `200.html` или `_redirects` — не используйте их. Названия разделов после `#/` команда выбирает под свою тему — в игре это могут быть, например, `#/play` и `#/scores`.
- В `index.html` внутри `<body>` нет вёрстки интерфейса: допустимы строка подключения js-файла и один пустой корневой контейнер вроде `<div id="app"></div>`, который добавляет шаблон Vite. Весь интерфейс создаётся кодом на TypeScript через DOM API.
- UI-фреймворки (React, Vue, Angular и т. п.) не используются.
- При открытии ссылки `#/...` напрямую нужный экран восстанавливается; кнопка «назад» в браузере работает.

#### 2. Экраны — минимум 3

| Экран                        | Что на нём                                                                                                                                  |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| «О нас» (открывается первой) | что делает приложение, состав команды, краткий вклад каждого; **кнопка/ссылка, ведущая к основной работе**                                  |
| Главная страница             | данные приложения: каталог, список, уровни — по теме проекта                                                                                |
| Страница результатов         | корзина, избранное, история выполненных действий, таблица результатов — по теме проекта; для списка задач — выполненные задачи и статистика |

- Меню доступно на всех экранах; «О нас» открыта в любой момент.
- Попапы и диалоги разрешены — например, подтверждение действия или сообщение об ошибке поверх текущей страницы. Но все экраны должны быть **самостоятельными состояниями приложения со своим адресом**: экран считается экраном, если при его открытии меняется адрес, он восстанавливается после перезагрузки и по кнопке «назад». Попап без адреса экраном не считается.

#### 3. Данные и их хранение

- Справочные данные приложения (товары, фильмы, уровни…) лежат в самом проекте: TypeScript-модулем или JSON-файлом, загружаемым при старте. При наличии бэкенда они могут приходить с сервера.
- Каждая сущность описана TypeScript-интерфейсом с уникальным `id` и минимум тремя полями (кроме `id`).
- **Правило сохранения состояния: всё важное, что пользователь сделал или изменил за время работы в приложении, должно быть видно после перезагрузки страницы.** Без бэкенда для этого используется `localStorage`. Что именно сохраняется, зависит от темы:

| Тема                       | Что сохраняется                          |
| -------------------------- | ---------------------------------------- |
| Магазин                    | корзина                                  |
| Игра                       | таблица результатов, рекорды, прогресс   |
| Список задач / планировщик | добавленные задачи и события, их статусы |
| Каталог фильмов и т. п.    | избранное, оценки                        |

#### 4. Главная страница

- **Ориентир — 8–12 элементов данных**, с которыми работают на главной странице: товары, задачи, фильмы… Количество элементов никто не проверяет и штрафом оно не является — обязательны действия с данными, о которых идёт речь ниже. Для игры таких элементов может не быть: тогда главный экран — это сам игровой процесс, а три действия относятся к нему (сложность, режим, рестарт). Делать несколько уровней не обязательно.
- **3 вида действий** с данными, например: поиск по части названия без учёта регистра + 1–2 фильтра + сортировка. Для игры и других нестандартных тем — свои три действия по теме (выбор сложности, режима, повтор уровня), но они должны менять то, что видит пользователь.

#### 5. Страница результатов — меняет состояние

- **Минимум два действия пользователя меняют данные**: добавить/удалить, количество, статус, законченное действие в игре... По желанию добавляют третье действие — промокод или скидку, тогда итог пересчитывается от общей суммы.
- Итоговые величины пересчитываются на глазах: сумма, количество, рекорд, среднее.

#### 6. Инструменты и качество

Обязательны, но отдельно баллами не оцениваются и штрафам не подлежат — проверяющий не запускает проект и не изучает код. На баллы влияют косвенно: функцию для live coding берут из этого модуля, а 25 баллов за live coding включают показ подготовленных тестов.

- Бизнес-логика отделена от отрисовки: есть модуль с функциями, которые работают с данными, не трогая DOM, — из него выбирают функцию для live coding.
- Для этого модуля написаны подготовленные unit-тесты, запускаемые одной командой (`npm test`).
- TypeScript со `strict`: в рекомендованном шаблоне Vite `vanilla-ts` он включён по умолчанию — просто не отключайте его.
- Обратную связь пользователь получает на странице (сообщения, подсветка полей); системные окна браузера `alert`, `confirm`, `prompt` не используются.

#### 7. Не требуется

Регистрация и вход, настоящая авторизация, оплата, бэкенд, база данных, хеширование паролей, сложный дизайн и адаптивность — **не требуются и не оцениваются**, но приветствуются.

#### 8. Как подтвердить на записи (сценарий демонстрации)

1. Откройте опубликованный адрес приложения — видна страница «О нас», видна кнопка перехода к основной работе.
2. Пройдите все экраны через меню; покажите адресную строку (адрес меняется) и кнопку «назад».
3. Покажите работу поиска/фильтров/сортировки на главной — чтобы было видно, как список меняется.
4. На странице результатов выполните два действия с данными и покажите, как меняются итоги.
5. Перезагрузите страницу, не меняя адреса в строке браузера, — должен восстановиться тот же экран и сами результаты (корзина, рекорды).
6. Один раз покажите исходный код страницы (`Ctrl+U`): в `<body>` нет вёрстки интерфейса. Затем в редакторе кода откройте `package.json`: в зависимостях нет UI-фреймворков.

## Часть 2. Организация командной работы

1. Создайте доску задач в Jira, GitHub Projects или аналогичном инструменте. Добавьте задачи, назначьте ответственных и отмечайте движение работы, например: «Запланировано», «В работе», «На ревью», «Готово».
2. Создайте общий репозиторий. Договоритесь, как будете называть ветки, создавать коммиты и объединять изменения.
3. Работайте над задачами в отдельных ветках и открывайте Pull Request в общий репозиторий. Посмотрите изменения друг друга и оставьте обратную связь.
4. Обсуждайте решения и сложности по ходу работы. Если распределение задач меняется, обновляйте доску.

Заранее договоритесь о времени встреч, канале связи и том, как поступите, если кто-то задерживается. Разделите работу так, чтобы оба участника могли рассказать о своём вкладе и получили опыт работы с доской, ветками и ревью.

## Часть 3. Интервью

Проведите **два отдельных интервью**: в каждом один участник — кандидат, второй — интервьюер. Затем поменяйтесь ролями. Ориентир — 15–30 минут на одно интервью, из них примерно 3–5 минут на демонстрацию приложения по сценарию технического минимума и 7–10 минут на live coding; важнее раскрыть пункты ниже, чем попасть в точное время.

Запись интервью также может пригодиться на следующих этапах обучения: менторы смогут посмотреть её при выборе студентов, чтобы познакомиться с вашим опытом, проектом и подходом к решению задач.

Запишите разговор и демонстрацию экрана. Камера необязательна: голоса участников должны быть слышны, а показанные приложение, код и результаты тестов — читаемы. Перед записью договоритесь о ней и о том, как предоставить доступ проверяющим. Видео можно разместить, например, на YouTube с доступом по ссылке или на Google Диске, включив просмотр для всех, у кого есть ссылка. Откройте ссылку в режиме инкогнито и убедитесь, что видео доступно без запроса разрешения и входа в аккаунт.

### Пример структуры интервью

1. **Знакомство.** Кандидат представляется, рассказывает, что изучает и чем занимается.
2. **Проект и командная работа.** Кандидат показывает приложение и кратко объясняет его назначение. Показывает доску и репозиторий, рассказывает, как команда планировала задачи, взаимодействовала и проводила ревью, какие задачи выполнял лично он. Во время демонстрации приложения выполните [сценарий демонстрации](#8-как-подтвердить-на-записи-сценарий-демонстрации) из технического минимума.
3. **Вопросы о работе над проектом.** Интервьюер задаёт вопросы из списка ниже и уточняет детали ответов. Кандидат рассказывает о конкретных ситуациях, своих решениях и их результатах.
4. **Live coding (ориентировочно 7–10 минут).** Кандидат показывает функцию из проекта с несколькими сценариями, объясняет её назначение и ожидаемое поведение, предлагает варианты проверки и показывает запуск подготовленных тестов модуля (`npm test`). Затем во время записи пишет несколько содержательных unit-тестов, запускает их и объясняет результат. Если функция уже покрыта тестами, добавьте новые сценарии, например граничные случаи.

Функция для live coding должна существовать в вашем проекте. Примеры из гайда — расчёт корзины с промокодом или фильтрация товаров; промокод выбирайте только в том случае, если он действительно реализован, иначе берите расчёт суммы корзины или фильтрацию.

### Примеры вопросов для интервьюера

Выберите несколько вопросов, которые подходят вашему проекту; задавать все вопросы необязательно. Можно добавить свои и уточнять ответы кандидата.

- Какую задачу в проекте вы выполняли лично и как подошли к её решению?
- С какой сложностью вы столкнулись? Как вы нашли её причину и что помогло её преодолеть?
- Расскажите о решении, для которого вы рассматривали несколько вариантов. Почему выбрали именно этот и от чего пришлось отказаться?
- Как вы проверяли, что написанная вами функциональность работает правильно?
- Как команда распределяла задачи и что происходило, если планы менялись?
- Были ли у вас разные мнения с напарником? Как вы пришли к общему решению?
- Расскажите о замечании на code review: что предложили изменить и почему?
- Что бы вы улучшили в проекте, если бы у вас было больше времени? Почему?

Функцию для live coding можно выбрать заранее, как и подготовить проект к запуску тестов. Тесты для демонстрации пишутся во время записи. Если тест не прошёл, покажите результат и объясните, как будете искать причину: оценка учитывает ход рассуждений и действия, а не только успех с первой попытки.

## Как сдавать

У команды один общий проект, но **каждый студент сдаёт свою запись отдельно**.

1. Создайте в общем репозитории отдельную ветку для своей сдачи от `main` после объединения нужных изменений проекта.
2. Добавьте в ней файл с информацией о своей работе, например `submissions/github-username.md`, где `github-username` — ваш логин. Укажите:
   - ваше имя или GitHub-логин и имя или GitHub-логин напарника;
   - что делает приложение и какие задачи вы выполняли;
   - ссылку на деплой, общий репозиторий и доску задач;
   - ссылку на **ваше интервью в роли кандидата**.
3. Откройте Pull Request из своей ветки в `main` общего репозитория и не мержите его до окончания проверки. В описании PR разместите те же сведения и ссылки, включая ссылку на видео.
4. Проверьте доступность видео, звука, изображения экрана и ссылок для человека вне команды. Если доска закрыта, покажите её содержание на записи.
5. Отправьте ссылку на **свой Pull Request** через [RS App](https://app.rs.school/) → **Cross-Check: Submit** до дедлайна.

Если участник не выходит на связь, заранее сообщите организаторам курса и согласуйте вариант продолжения работы. Интервью можно провести с другим участником курса или волонтёром, рассказав о собственном вкладе в проект.

## Cross-check

Задание проверяется через [cross-check](https://rs.school/docs/cross-check-flow). Откройте отправленный PR, найдите в описании ссылку на интервью, затем оцените **запись, в которой автор PR — кандидат**. Проверяющему не нужно запускать проект, проверять каждую функцию приложения или оценивать дизайн.

Если видео недоступно, невозможно установить, кто кандидат, либо звук или изображение экрана не позволяют проверить пункт, соответствующий результат нельзя подтвердить. Учитывайте только то, что показано или объяснено на записи; при технических проблемах следуйте правилам cross-check курса.

## Критерии оценки

**Максимальный балл: 300**

Сумма баллов по всем пунктам больше 300 — это специально сделанный запас, который сглаживает неточности проверки и разное понимание требований. Итоговый балл всё равно ограничен сверху 300. Все пункты оцениваются по записи интервью автора PR; баллы и формулировки пока можно обсудить.

### Общие правила проверки

- Учитывайте только то, что **показано или объяснено на записи**: не показано — не засчитано. Запускать проект и изучать код проверяющему не нужно.
- Оценивайте содержание и продемонстрированные действия, а не качество речи, акцент или оформление проекта. Удачно обнаруженная и объяснённая ошибка в тесте — часть работы; оценивайте показанные действия и рассуждения.
- Сначала выставьте баллы по всем критериям, затем примените **штрафы** (подраздел «Штрафы»).

### Знакомство

1. Кандидат представился и кратко рассказал о себе и обучении: **+30**

### Проект

Каждый пункт засчитывается, если он не только показан, но и объяснён на записи.

1. Кандидат продемонстрировал приложение и объяснил его назначение: **+20**
2. Показал доску задач: задачи, ответственные, движение работы; объяснил, как команда планировала задачи: **+20**
3. Показал репозиторий и Pull Request: ветки, изменения; рассказал о ревью: **+25**
4. Рассказал о личном вкладе: какие задачи выполнял он, какие — напарник: **+20**
5. Рассказал, как проходили обсуждение решений и ревью: замечания, изменения, договорённости: **+25**

### Вопросы

Интервьюер задаёт вопросы о работе над проектом; баллы начисляются отдельно за каждый элемент ответа кандидата.

1. Интервьюер задал не менее двух вопросов о работе над проектом: **+10**
2. Кандидат показал конкретную сложность или решение в проекте: ситуацию и суть: **+20**
3. Объяснил рассмотренные варианты и почему выбрал один, от чего отказался: **+25**
4. Рассказал о результате: что вышло из решения, как оно себя показало: **+25**

### Live coding

1. Кандидат показал функцию из проекта, объяснил её назначение, поведение и сценарии проверки, показал запуск подготовленных тестов модуля: **+25**
2. Написал во время записи несколько содержательных unit-тестов: **+55**
3. Запустил тесты и разобрал результат: что проверяет каждый тест; при упавшем тесте — как будет искать причину: **+30** Ход рассуждений ценится выше успеха с первой попытки.

### Штрафы

Штрафы вычитаются из суммы баллов всех критериев (но не ниже 0). Каждый штраф применяется однократно, сколько бы нарушений под него ни попало:

1. **Приложение не работает или нарушен любой пункт технического минимума, видимый на записи**: не продемонстрировали приложение или оно не открывается по ссылке; экраны переключаются полной перезагрузкой; «О нас» не первая или не все три экрана со своими адресами; на главной меньше трёх действий с данными (для игр главный экран — сам процесс: считаются действия игрового процесса по теме, см. пункт 4 технического минимума); на странице результатов действия не меняют данные или итоги не пересчитываются; после перезагрузки результат не восстановился; в `package.json` видны UI-фреймворки: **−150 баллов**

Триггером считается только то, что показывает кандидат: требования сценария демонстрации (пункт 8 технического минимума) и кадры `Ctrl+U` и `package.json` в редакторе кода. Пункты, которых в этом списке нет (в том числе пункт 6 «Инструменты и качество»), штрафам не подлежат.
