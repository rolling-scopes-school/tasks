# Bulls and Cows

## Навыки

`JavaScript` `TypeScript` `функциональное программирование` `чистые функции` `иммутабельность` `рекурсия` `каррирование` `мемоизация` `TDD` `FIRST` `Jest/Vitest` `Big O` `ESLint` `Prettier` `Husky`

## Что делать

[Bulls and Cows](https://en.wikipedia.org/wiki/Bulls_and_Cows) — игра в угадывание секретного числа из уникальных цифр. Компьютер загадывает число заданной длины в заданной системе счисления, игрок вводит варианты, после каждой попытки получает подсказку: сколько цифр угаданы и стоят на своём месте (**bulls**), и сколько угаданы, но стоят не на своём месте (**cows**). Игра идёт до тех пор, пока игрок не угадает число — лимита попыток нет, но число попыток и время влияют на результат в таблице рекордов.

Это задание — не про интерфейс, а про архитектуру. Вся игровая логика должна быть написана в функциональном стиле: чистые функции без побочных эффектов, неизменяемые структуры данных, функции высшего порядка, каррирование, мемоизация и рекурсия — не как абстрактные упражнения, а как естественный способ решить конкретные задачи этой игры.

Пишете вы это по TDD: сначала падающие тесты на логику (отдельными коммитами), затем код, который их зажигает зелёным.

### Игровая логика (обязательные функции)

Ядро игры — чистые функции без классов. Ниже — не весь список заданных для реализации функций, а минимум, который проверяется явно:

- **`generateSecret(length, base, random = Math.random)`** — генерирует секретное число (секретное число рекомендуется представлять в виде строки или массива символов, чтобы корректно обрабатывать лидирующие нули, например, 0123 для длины 4): `length` уникальных цифр в системе счисления `base`. Функция **обязательно принимает источник случайности параметром** — это и есть приём, который делает генерацию тестируемой чистой функцией: в тестах вы передаёте детерминированный `random`, и результат становится предсказуемым.
- **`evaluateGuess(secret, guess)`** → `{ bulls, cows }` — сравнивает попытку с секретным числом. Реализуйте через методы массивов (`map`/`filter`/`reduce`), а не через ручные циклы со счётчиками — это и есть использование функций высшего порядка по существу задачи, а не для рендера.
- **`isValidGuess(guess, length, base)`** — проверяет: длина совпадает, все символы — допустимые цифры для `base`, цифры не повторяются.
- **`createDigitValidator(base)`** → `(char) => boolean` — каррированная фабрика: по системе счисления возвращает функцию-предикат «этот символ — допустимая цифра в этой системе». Используется и в `isValidGuess`, и при вводе в реальном времени (блокировка недопустимых символов).
- **`countPossibleSecrets(length, base)`** — считает, сколько существует различных секретных чисел при данных `length` и `base` (количество перестановок без повторений). Реализуйте **рекурсивно** (через связь `countPossibleSecrets(length, base) = base * countPossibleSecrets(length - 1, base - 1)`-подобную формулу), а затем **мемоизируйте** результат — функция вызывается при каждом открытии настроек и при каждой подсказке «сколько вариантов осталось», пересчитывать заново незачем.
- Состояние игры (история попыток, текущие настройки, статус) должно обновляться **иммутабельно**: каждая попытка добавляет новую запись в историю через создание нового массива (`[...history, entry]`), а не через `push`/мутацию существующего объекта состояния.

Если видите естественное место для ещё одной чистой функции, HOF, каррирования или мемоизации — используйте; списком выше покрывается то, что проверяется по чек-листу, не более.

### Игровой процесс

- **Настройки перед игрой**: выбор длины секретного числа (3–6 цифр) и системы счисления (bin / oct / dec / hex). Настройки нельзя менять после старта раунда.
- **Поле ввода попытки**: принимает только допустимые для выбранной системы символы (используйте `createDigitValidator`).
- **История попыток**: после каждой попытки в список добавляется запись — сама попытка и результат (`bulls`/`cows`). Старые записи не меняются и не удаляются.
- **Окончание игры**: как только `bulls === length`, игра засчитывается как выигранная, засчитывается количество попыток и время с начала раунда.
- **Таблица рекордов**: топ-N лучших результатов (по числу попыток, при равенстве — по времени), хранится в `localStorage`, переживает перезагрузку страницы. Учитывайте длину/систему счисления раунда — результаты в разных настройках не должны обесценивать друг друга в одном общем рейтинге без пометки, в каких настройках они достигнуты.
- **Новая игра**: возврат к экрану настроек без перезагрузки страницы.

## Требования

### Настройка проекта

- TypeScript обязателен для всей логики и UI.
- ESLint, Prettier, Husky + lint-staged — настроены и работают (как в задаче Clean Code, неделя 7).
- `package.json` содержит скрипты `lint`, `format`, `test`.
- **Бандлер не обязателен** — он будет на неделе 11–12. Компилируйте TS обычным `tsc` в ES-модули и подключайте результат в `index.html` через `<script type="module">`. Если хочется использовать бандлер — не запрещено, но не требуется и не даёт дополнительных баллов.
- Jest/Vitest для тестов (любой на ваш выбор).

### TDD и порядок коммитов

Для каждой из обязательных функций ядра (раздел выше):

1. Отдельный коммит с **падающими** тестами на функцию, написанными по принципам **FIRST** (Fast, Independent, Repeatable, Self-validating, Timely) — тесты написаны раньше реализации и действительно падают на пустой/заглушечной реализации.
2. Отдельный коммит с реализацией, после которого тесты становятся зелёными.

Коммиты настройки инструментов, UI и документации — отдельно от тестов и логики.

### Архитектура

- `body` в `index.html` пустой (кроме `<script>`) — вся разметка генерируется кодом.
- Игровая логика (генерация, валидация, сравнение, подсчёт, иммутабельные обновления состояния) не зависит от DOM и может быть протестирована без браузера.
- Классы для игровой логики не используются — она должна читаться как набор чистых функций.
- Никакого `innerHTML`/`insertAdjacentHTML` для динамического контента.

### Документация — `DESIGN.md`

Отдельный файл в корне репозитория. Должен содержать:

1. **Структуры данных и алгоритмы**: какие структуры использованы для состояния игры и истории попыток, и почему; описание алгоритма `evaluateGuess` и `countPossibleSecrets`.
2. **Сложность**: Big O для `generateSecret`, `evaluateGuess`, `isValidGuess`, `countPossibleSecrets` — с коротким обоснованием, не просто цифрой.
3. **Принципы чистого кода**: какие принципы (из модуля Clean Code) применены в этом проекте и где конкретно — с указанием файла/функции, не абстрактно.

## Чек-лист поведения

Пройдите руками на своём деплое и отметьте в описании PR.

- [ ] Настройки длины (3–6) и системы счисления (bin/oct/dec/hex) доступны до старта и блокируются после
- [ ] Поле ввода не принимает символы, недопустимые для выбранной системы счисления
- [ ] После каждой попытки появляется новая запись в истории с числом bulls/cows
- [ ] Повторный ввод уже использованной попытки не ломает историю и не считается новой записью задвоением логики (на ваше усмотрение, как обработать — главное, без ошибок)
- [ ] При угадывании секретного числа игра корректно завершается, засчитывается число попыток и время
- [ ] Результат попадает в таблицу рекордов, рекорды переживают перезагрузку страницы
- [ ] «Новая игра» возвращает к экрану настроек без перезагрузки страницы

## Чего делать не нужно

- Не делать бэкенд и не подключать внешние API — секретное число генерируется на клиенте.
- Не оборачивать игровую логику в классы «чтобы было похоже на ООП» — задание именно про функциональный стиль.
- Не писать реализацию раньше тестов для функций из обязательного списка — порядок коммитов проверяется.
- Не использовать сторонние библиотеки для самой игровой логики (lodash и подобные) — цель задания написать чистые функции, HOF, каррирование и мемоизацию руками.
