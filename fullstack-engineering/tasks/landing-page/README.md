# Landing Page

## Описание проекта

Landing Page — учебный проект, в котором вам предстоит создать адаптивный двухстраничный сайт и добавить интерактивность на чистом JavaScript.

Задание состоит из двух частей, каждая из которых рассчитана на одну неделю. В первую неделю вы выполните семантическую адаптивную вёрстку и реализуете переключение между светлой и тёмной темами с сохранением выбора пользователя. Во вторую неделю добавите основную интерактивность.

Вы можете работать по готовому макету **Coffee House** или создать собственный проект. Оба варианта имеют одинаковый набор обязательных элементов и позволяют получить максимальный балл.

## Варианты выполнения

### Вариант 1. Coffee House

Если вы впервые работаете с Figma, только осваиваете адаптивную вёрстку или хотите сосредоточиться на технической реализации проекта, рекомендуем выбрать [готовый макет Coffee House](https://www.figma.com/design/yuc5s9NCc4jENkk5LdFfvX/Coffee-House-2026Q3?node-id=0-1).

В макете уже подготовлены структура, контент, адаптивные версии страниц и две цветовые темы. Вам не придётся самостоятельно продумывать дизайн — можно сразу перейти к его реализации.

### Вариант 2. Авторский проект

Если вы уже уверенно верстаете и готовы самостоятельно принимать решения о структуре и внешнем виде сайта, вы можете реализовать собственную идею без готового макета. Выберите тему, которая вам действительно интересна, продумайте визуальный стиль проекта и создайте уникальную работу.

Этот вариант даёт больше творческой свободы. В результате вы получите самостоятельную работу для портфолио, а не ещё одну реализацию знакомого учебного макета. Авторские проекты также сделают cross-check интереснее: проверяя их, студенты смогут познакомиться с разными идеями и подходами к разработке. Наиболее интересные работы можно будет вместе посмотреть и обсудить на стриме.

> Создавать макет в Figma для авторского проекта не требуется. Оба варианта выполнения оцениваются по одному чек-листу и позволяют получить максимальный балл.

## Выбор темы лендинга

Тему можно придумать полностью самостоятельно. Если пока нет идеи, можно взять один из примеров:

- кофейня / кафе
- спортзал / фитнес-студия
- языковые курсы
- стоматология / клиника
- барбершоп
- бьюти-салон
- IT-курс / буткемп
- SaaS-продукт / стартап
- музыкальная группа
- благотворительное событие
- доставка еды
- автосервис
- приют для животных

Тема должна допускать естественное появление всех обязательных блоков задания: карточек для слайдера/карусели (услуги, меню, отзывы, портфолио и т.п.), формы заявки/записи/обратной связи и модального окна. Если тема настолько специфична, что это невозможно, лучше выбрать другую.

## Обязательная структура проекта

Независимо от выбранной темы проект должен включать:

- две связанные страницы — главную и каталог;
- общие для обеих страниц `header` и `footer`;
- навигацию и переключатель светлой и тёмной тем;
- не менее четырёх контентных секций на главной странице;
- каталог с категориями и карточками;
- адаптивную вёрстку для десктопных, планшетных и мобильных экранов;
- интерактивность, предусмотренную требованиями обеих частей задания.

Подробные требования к структуре, вёрстке и функциональности приведены в README соответствующей части.

## Этапы работы

### [Часть 1. Вёрстка](README-part-1.md)

- две страницы;
- семантическая вёрстка;
- визуальное оформление проекта;
- адаптивность от 1440px до 380px;
- светлая и тёмная темы;
- переключение темы и сохранение выбора в `localStorage`.

### [Часть 2. Функциональность](README-part-2.md)

- бургер-меню;
- слайдер или карусель;
- переключение категорий и отображение дополнительных карточек;
- модальное окно с информацией о выбранной карточке;
- выбор параметров карточки и динамическое обновление связанной информации в модальном окне без перезагрузки страницы.

## Общие технические требования

1. Вёрстка должна быть валидной, семантической и адаптивной.
2. Проект должен корректно отображаться и работать в последней версии Google Chrome.
3. Для реализации функциональности используется чистый JavaScript.
4. Использование CSS-фреймворков, например Bootstrap, не допускается.
5. Использование JS-фреймворков, например React, Angular или Vue, не допускается.
6. Использование TypeScript не допускается.
7. Использование HTML-препроцессоров и шаблонизаторов, например Pug, не допускается.
8. Нельзя использовать готовые библиотеки компонентов и интерактивности, в том числе библиотеки для слайдеров, модальных окон и бургер-меню. Вся проверяемая функциональность должна быть реализована самостоятельно.
9. Допускается использование CSS-препроцессоров (`SASS`, `SCSS`) и `modern-normalize`.
10. Допускается использование сборщиков, например Vite или Webpack. При их использовании должны быть включены source maps.
11. Код должен быть читаемым, без минификации и обфускации.
12. Нельзя заменять вёрстку всего макета или отдельных блоков скриншотами. Изображения используются только как самостоятельный контент: фотографии, иллюстрации и иконки.

## Требования к репозиторию

- Задание выполняется в личном публичном репозитории `rsschool-landing-page`.
- Ветка `main` должна оставаться пустой. В ней могут находиться только служебные файлы, например `README.md`, `.gitignore` или папка `.github`.
- Часть 1 выполняется в ветке `landing-page`, созданной от `main`. После завершения Части 1 откройте Pull Request из `landing-page` в `main`. Не мержите и не закрывайте его.
- Часть 2 выполняется в ветке `landing-page-part-2`, созданной от `landing-page`. После завершения Части 2 откройте Pull Request из `landing-page-part-2` в `landing-page` и выполните merge. Изменения автоматически появятся в открытом Pull Request из `landing-page` в `main`.
- После merge вручную обновите описание Pull Request из `landing-page` в `main`, добавив информацию о выполнении Части 2. Не мержите и не закрывайте этот Pull Request.
- Каждый Pull Request оформляйте в соответствии с [требованиями к Pull Request](https://rs.school/docs/short-track/pull-request-requirements).
- Внутренняя структура проекта остаётся на усмотрение студента.
- История коммитов должна отражать процесс разработки. Названия коммитов оформляются согласно [руководству RS School](https://rs.school/docs/git-convention).

## Оценивание

Каждая часть задания оценивается отдельно через [cross-check](https://rs.school/docs/cross-check-flow).

В рамках каждой части на платформе используется один общий чек-лист для всех работ. Студенты, выполнившие Coffee House, и студенты, создавшие авторский проект, проверяются по одним и тем же критериям.

Максимальный балл, правила сдачи, критерии и штрафы приводятся отдельно для каждой части.
