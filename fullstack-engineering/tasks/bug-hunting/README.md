# Bug Hunting

## Что делать

Перед вами готовый проект из пяти небольших страниц. Всё выглядит почти работающим, но в код специально внесли **45 багов**: часть ломает вёрстку (CSS), часть — логику (JavaScript). Ваша задача — как настоящий разработчик, который получил чужой проект с багрепортом, найти и исправить каждый баг, опираясь на описание ожидаемого поведения.

Стартовый проект лежит в репозитории [Rss-bug-hunting](https://github.com/OreskaG/Rss-bug-hunting). Полный список багов по каждой странице (в формате «что не так → как должно быть») находится в его `README.md` — это и есть ваш багрепорт. HTML-разметка на всех страницах **корректна** и показывает, каким должен быть итог; исправлять нужно только CSS и JavaScript.

Пять заданий с растущей сложностью:

| #   | Страница             | Тип багов  | Багов |
| --- | -------------------- | ---------- | ----- |
| 1   | Прайс-таблица        | CSS        | 8     |
| 2   | Портфолио-галерея    | CSS        | 7     |
| 3   | Список задач (To-Do) | JavaScript | 10    |
| 4   | Корзина              | JavaScript | 10    |
| 5   | Каталог с фильтрами  | JavaScript | 10    |

## Требования

- Задание выполняется в **личном публичном форке** репозитория [Rss-bug-hunting](https://github.com/OreskaG/Rss-bug-hunting).
- Исправляйте только **CSS и JavaScript**, структуру HTML менять не нужно — она корректна и задаёт эталонный результат.
- Баги исправляются в соответствии с описанием в багрепорте (README форка).
- Ведите историю коммитов по [конвенции коммитов](https://rs.school/docs/git-convention).
- Работа проверяется в последней версии Google Chrome.

## Как сдавать

1. Сделайте **Fork** репозитория [Rss-bug-hunting](https://github.com/OreskaG/Rss-bug-hunting) к себе на GitHub.
2. Создайте ветку от `main` (например, `fix/bugs`) и исправляйте баги, коммитя по ходу работы.
3. Откройте **Pull Request из ветки с исправлениями в свой `main`** (не в `main` оригинального репозитория). Не мержите его — на проверку отправляется ссылка именно на этот Pull Request.
4. Задеплойте свою версию проекта, чтобы её можно было открыть по ссылке. Подойдёт любой хостинг статических страниц — например, GitHub Pages или Netlify.
5. [Оформите описание Pull Request по схеме](https://rs.school/docs/mentoring/pull-request-review-process#pull-request-requirements-pr) и добавьте в него ссылку на деплой.

## Cross-check

Задание проверяется через [cross-check](https://rs.school/docs/cross-check-flow). После выдачи задания, но до дедлайна зайдите в [rs app](https://app.rs.school/), выберите **Cross-Check: Submit**, в выпадающем списке выберите название задания, в поле **Solution URL** добавьте ссылку **на Pull Request** и нажмите **Submit**.

## Критерии оценки

**Максимальный балл: 200**

Каждый исправленный баг оценивается в **+5 баллов**. Всего 45 багов — по ним максимально набирается 225 баллов; это сознательный запас (~12%), который сглаживает неточности проверки. Итоговый балл всё равно ограничен сверху 200.

Полный перечень багов с описанием «что не так → как должно быть» — в [README стартового репозитория](https://github.com/OreskaG/Rss-bug-hunting). Баллы по заданиям:

1. Задание 1. Прайс-таблица — 8 багов: **+40**
2. Задание 2. Портфолио-галерея — 7 багов: **+35**
3. Задание 3. Список задач (To-Do) — 10 багов: **+50**
4. Задание 4. Корзина — 10 багов: **+50**
5. Задание 5. Каталог с фильтрами — 10 багов: **+50**

### Штрафы

- Pull Request оформлен не по схеме или в его описании нет ссылки на рабочий деплой: **-100**
- История коммитов не ведётся или коммиты не соответствуют [конвенции](https://rs.school/docs/git-convention): **-100**
